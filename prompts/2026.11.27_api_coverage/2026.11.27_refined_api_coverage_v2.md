# Refined prompt v2 — Siigo API coverage

**Goal.** Compare the current Siigo API documentation (API Blueprint at siigoapi.docs.apiary.io, downloaded 2026-11-27) with the MCP tool catalog (version 2026-10-15, app 0.2.0). Plan how to cover the whole API safely. Owner decisions A1–A10 were made on 2026-11-27 (below). This version replaces v1.

## Findings

- All read endpoints are covered (45 read tools). 23 write endpoints are missing (9 write tools today).
- Missing: delete product; create/update account groups; update, annul, delete, email, and batch for sales invoices; create/update/delete for quotations, purchase invoices, and support documents; create (simple and `Detailed`) and delete for payment receipts; create/update/delete for webhooks. `POST /auth` stays internal.
- Docs typos: quotation delete is printed as `/v1/invoices/id`, and purchase delete as `/v1/pruchases/id`.

## Updates to the shipped tools

- U1 (bug): `siigo_create_voucher_misc_income` schema allows only `type: "Detailed"`. The docs require `"MiscIncome"` and `income.id`.
- U2: `siigo_create_voucher`: remove `Detailed`, and add taxes and discounts on the due.
- U3: `siigo_create_invoice`: health-sector fields of Resolution 948 (`healthcare_company`, `nonContractInvoiceReason`, and related fields).
- U4: `siigo_create_credit_note`: `healthcare_company.operation_type`.
- U5: customers: `additional_fields.CUCON`.
- U6: products: `Combo` type with `components` (Premium plan).
- U7: send `Idempotency-Key` on POST for invoices, credit notes, journals, and cash receipts.
- U8: remove the response fields that were copied as query filters into the document-type list tools.
- U9: confirm `GET /v1/journals/{id}`, `/v1/misc-incomes`, and `/v1/expenses` with live reads.

## Proposed risk levels

Create/update (today's rules); Permanent (delete and annul: one by one in the Siigo window, never "similar" or automatic); Sends outside (email and webhooks: never automatic or "similar"; addresses and URLs shown in full; https only); Bulk (batch: Siigo window only, counts as N writes). These rules only make approval stricter (CLAUDE.md rule 3).

## Phases

10 catalog refresh and fixes; 11 risk levels in the approval flow; 12 new create/update tools (11); 13 delete and annul (7); 14 email, webhooks, and batch (up to 5); 15 docs and release v0.3.0.

## Owner decisions (2026-11-27)

| # | Decision | Choice |
|---|---|---|
| A1 | Scope | Add 22 of the 23 endpoints in phases 12–14. The invoice batch is left out (A5). |
| A2 | Delete and annul approval | Only one by one in the Siigo window, never by "approve similar" or automatic approval, even in "AI app" mode. The window reads the record first and shows its name, number, customer, and total, with a red "Can't be undone" banner. |
| A3 | Invoice email | Add it. Every address is shown in the approval window. Never approved automatically or by "similar". |
| A4 | Webhook writes | Add create, update, and delete. https URLs only, shown in full. Never approved automatically or by "similar". Deleting a webhook follows A2. |
| A5 | Invoice batch | Not now. Review again if the owner needs it. Keep it in the build script's excluded list with this reason. |
| A6 | Idempotency-Key | The app makes the key from the request content (tool + body) on POST for invoices, credit notes, journals, and cash receipts. When Siigo returns an existing document, the tool result says so. To create an identical document on purpose, change something small (for example, the observations). |
| A7 | Catalog source | Copy the YAML into the repository as a development-only file. It is not shipped, and CI can rebuild and check `catalog.json`. |
| A8 | Fake filters | Remove them from the document-type list tools. |
| A9 | Real Siigo tests | Mock tests only. The U9 paths keep their current values (from the owner's earlier catalog) and are marked as not verified in the docs. Release candidates (`-rc.N`) are the place to catch differences. |
| A10 | Releases | Release v0.2.1 after phase 10, then v0.3.0-rc.1 after phase 14, and v0.3.0 at the end. |
