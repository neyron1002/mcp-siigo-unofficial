## 2026-11-18 · Phase 1, Siigo client + vault (branch `phase-1-siigo-vault`)

- Owner prompt (raw `2026.11.18_raw_execute_plan_status.md`): "Execute the plan. What is the status?"
- Runtime dependencies added (all from the plan's audited list, section 3.2): `httpx`, `cryptography`, `keyring`, `platformdirs`.
- Built:
  - `paths.py`: per-user data folder per OS (plan D9), with the `MCP_SIIGO_UNOFFICIAL_HOME` override for tests and the self-test.
  - `vault/`: AES-256-GCM field encryption (the field name is bound as associated data), a master key in the OS keychain (`keyring`), SQLite in WAL mode with `meta`, `secrets`, `settings`, and `events` tables, a key-check record, and owner-only file permissions on POSIX. A missing or wrong key raises an error instead of silently replacing the key; `Vault.reset` is the explicit way out.
  - `siigo/`: credentials with the Partner-Id rule (3–100 alphanumeric characters) and a `repr` that hides the key; an async client with token caching and renewal 5 minutes before expiry, one re-authentication on 401, `Retry-After` handling on 429 (capped at 60 s, 2 retries), one retry for reads on network errors and 502/503/504 (never for writes), a `/v1/`-only path guard, and readable Siigo errors.
  - `tests/mock_siigo.py`: a mock Siigo API (auth, Partner-Id, tokens, paginated lists, catalogs, CRUD for customers, products, and invoices, fault injection), in-process or over HTTP on 127.0.0.1.
  - `scripts/with-test-keyring.sh`: a temporary Secret Service keychain for Linux tests.
- Verified in the container: ruff, mypy strict, 67 tests passed, and the real-keychain round trip passed with the temporary Secret Service.
- Deviation: none from the plan. Note: the plan's `server/` and phase 2 will reuse the owner's endpoint catalog from `references/`.
- Pull request: https://github.com/neyron1002/mcp-siigo-unofficial/pull/2. CI green: 68 tests passed with none skipped on windows-latest (Credential Manager), macos-latest (Keychain), and the Linux dev container job (temporary Secret Service), so the vault round trip with a real OS keychain passed on all 3 operating systems.

## 2026-11-18 · Phase 2, MCP server (branch `phase-2-mcp-server`)

- Owner prompt (raw `2026.11.18_raw_continue_plan.md`): "Continue executing the plan."
- Runtime dependency added: `mcp` 2.3 (pinned `>=2.3,<3`), which brings starlette, uvicorn, pydantic, and `httpx2`.
- Built:
  - `scripts/build_catalog.py` converts the owner's YAML catalog into `server/catalog.json` (81 KB, committed; PyYAML only at development time). English tool names (`siigo_list_invoices`, ...). **45 read tools** (every safe read endpoint) and **9 write tools** (plan section 5 scope: create/update customers and products; create invoices, credit notes, cash receipts (2 kinds), and journals). Deletes, annulments, emails, batches, quotations, purchases, support documents, payment receipts, and webhooks writes are left out on purpose.
  - `server/app.py`: one tool per endpoint, with the Siigo body schema in the input schema; read tools `readOnlyHint`, write tools `destructiveHint` and the "⚠ WRITE ACTION — REAL DATA IN SIIGO" block; a `siigo_status` tool; server instructions with the liability statement.
  - `server/write_gate.py`: the "Write actions" switch (off at start, needs an acceptance of responsibility, recorded in the vault event log) and one-time `confirmation_id`s (5 minutes, bound to the tool and the exact arguments).
  - Write approval: MCP elicitation when the client supports it (works on both the handshake protocol and the 2026-07-28 input-required flow, through the SDK's resolver), otherwise the two-step preview + `confirmation_id`. Write tools are hidden and rejected while the switch is off; each switch change sends `notifications/tools/list_changed` (and the 2026-07-28 subscription event), also when the switch changes from another thread (the tray).
  - `server/transport.py`: Streamable HTTP on `127.0.0.1` (uvicorn on a background thread), bearer key from the vault (constant-time check, 401 otherwise), the SDK's DNS-rebinding protection; `--stdio` mode follows the tray's switch through the vault. `__main__`: `--stdio` and `--serve`.
- Verified in the container: ruff, mypy strict, 101 tests passed (90% coverage), including "a write without confirmation is rejected", "write tools are hidden when the switch is off", elicitation approve/reject/decline in both protocol modes, HTTP 401 without the key, foreign Host rejected, and a real stdio subprocess.
- Deviations from the plan, with reasons:
  - **`httpx2` instead of `httpx`:** `mcp` 2.x depends on `httpx2` (same API) and no longer on `httpx`. The Siigo client moved to `httpx2`, so the build ships one HTTP library instead of two (about 1.5 MB less).
  - **No embedded Siigo documentation pages:** the owner's Markdown copies of Siigo's official docs (about 430 KB) are Siigo's text, so they are not published in this MIT repository. Each tool keeps the short official description, the body schema, notes, and a request example.
  - Two SDK internals are used (`MCPServer._handle_list_tools/_handle_call_tool` overrides and `ServerSession._connection`) to reach long-lived connections for notifications; the `mcp` pin and the tests guard them.
- Pull request: https://github.com/neyron1002/mcp-siigo-unofficial/pull/3. CI green: 102 tests passed on windows-latest, macos-latest, and the Linux dev container job (101 + 1 skipped on plain ubuntu-22.04, by design).

## 2026-11-18 · Phase 4, single-file build and release (branch `phase-4-single-file-build`)

- Owner prompts (raw `2026.11.18_raw_continue_phase_4.md`, `2026.11.18_raw_status_now.md`): "Please continue with phase 4." and status questions.
- Runtime dependency added: none. Build-only group: `pyinstaller` and `pyinstaller-hooks-contrib`.
- Built:
  - `launcher/core.py`: the single-file launcher for Windows and Linux. The downloadable file carries the one-folder app as an LZMA `payload.tar.xz`, its manifest (version, SHA-256), and the small `launcher-core`. The first run checks the SHA-256, extracts into `versions/<version>` (atomic rename, `tarfile` "data" filter), installs the small launcher, keeps the current and previous versions, and starts the app. Modes: default, `--run`, `--stdio`, `--selftest`, `--uninstall [--purge-data]`.
  - macOS: a `.app` (no Dock icon, macOS 13+) in an LZMA-compressed DMG (ULMO) with an Applications shortcut.
  - `packaging/`: PyInstaller specs (bytecode optimize level 1, no UPX, strip on macOS and Linux), PySide6 hook overrides plus `qt_filter.py` so only the Qt libraries, plugins, and translations the app uses are collected (this removed about 31 MB of GTK files on Linux), `build.py` (build, payload, DMG, size report, size budget with 10% tolerance), `smoke_test.py`, `build_bootloader.py` (PyInstaller bootloader compiled from source in CI), and `sign.py` (Ed25519 key generation, signing, and verification of `SHA256SUMS`).
  - `update/signature.py`: `SHA256SUMS` parsing and Ed25519 verification, for phase 5.
  - Workflows: `build.yml` (3 systems: build, smoke test in a clean temporary home, artifact upload; 30-minute limit), used by `ci.yml` on every pull request and by `release.yml` on `v*` tags (version check, build, sign, verify, GitHub release; pre-release when the tag has "-").
- First measured sizes (budgets set in `packaging/size_budget.json`):

  | Target | Download | Unpacked |
  |---|---|---|
  | windows-x64 (.exe) | 48.8 MB | 105.1 MB |
  | macos-arm64 (.dmg) | 29.0 MB | 87.2 MB |
  | linux-x64 | 60.0 MB | 140.1 MB |

- Problems fixed in CI:
  - Windows: excluding `distutils` clashed with PyInstaller's alias hook; the exclusion was removed.
  - Windows: the launcher is a GUI program, so the app it started got no stdin or stdout; `--selftest` hung on an error dialog (cancelled after 71 minutes). The launcher now passes its streams explicitly, and the smoke test kills the whole process tree on a timeout.
  - The launcher needed `xml` (used by `plistlib`), so it is no longer excluded.
- Deviations from the plan, with reasons:
  - **Bootloader compiled only in CI.** The permission system blocked cloning PyInstaller to compile it in the dev container; the local Linux ARM build used the stock bootloader (58.2 MB, smoke test passed).
  - **Release signing key not created yet.** The permission system blocked generating the key and running `gh secret set`. The owner must approve or run the commands. Until then `release.yml` stops at the version check (no public key), so no release tag was pushed.
