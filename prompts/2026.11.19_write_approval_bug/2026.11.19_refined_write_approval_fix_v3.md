## 2. New rule 3 (CLAUDE.md), approved by the owner

> **Write safety.** Siigo write tools are behind the "Write actions" switch: off by default, and off again after every restart. Turning it on needs the warning dialog and an acceptance of responsibility. Every write needs the user's approval, in the way the user chose in Settings: the Siigo window (default), a notification that opens it, or the AI app's question with the window as fallback. Approving similar writes, or automatic approval for a limited time, only happens when the user turns it on in the app, never from an MCP tool, and it ends at its time limit, its write limit, or at restart. Never weaken this further without the owner's decision.

Plan v8 section 5.1 gets the same change.

## 3. Design notes

- The HTTP server runs inside the tray app and opens the window directly.
- stdio processes reach the tray app through a private route on its existing local HTTP server (`127.0.0.1`, same bearer key, read from the vault). No QtNetwork, which is excluded for size (rule 2). If the tray app can't be reached, the write is refused.
- Writes are on only while the tray app runs, because quitting resets the switch. So an approval path always exists when writes are on.
- MCP progress notifications are sent while the window is open, to keep AI apps from stopping the wait.
- Messages to the AI: "Rejected in the Siigo approval window", "Nobody answered the approval window", "The Siigo app is not reachable".
- Fix the duplicate `required` items in the catalog schemas for `siigo_create_voucher_misc_income` and `siigo_create_journal`, and add a test against duplicates.
