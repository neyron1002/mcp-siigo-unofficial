# Refined prompt v1 — write approval fix (findings, plan, and decisions)

Raw prompts: `2026.11.19_raw_write_approval_bug.md`, `2026.11.19_raw_confirm_and_document.md`.
Status: **draft, waiting for the owner's decisions (section 5)**. Decision page: https://claude.ai/artifact/JzppDENqUooYtdgdkDDBxE.

## 1. Problem

With write actions on, every write in Claude Desktop ends at once with:

```json
{"status":"rejected_by_user","message":"The user did not approve siigo_create_product. Nothing was sent."}
```

No Approve/Reject question and no `confirmation_id` appear. Nothing is sent to Siigo.

| Where | Result | Checked by |
|---|---|---|
| Claude Code, interactive terminal | Works: the question appears | Owner, 2026-11-19 |
| Claude Desktop | Rejected without asking | Owner, 2026-11-19 |
| Claude Code non-interactive (`claude -p`) | Rejected without asking | Claude, reproduced 2026-11-19 |

## 2. Cause

1. The server picks the approval method from the client's capabilities ([app.py](../../src/mcp_siigo_unofficial/server/app.py), `_make_approval_resolver`): elicitation if the client declares it, otherwise the two-step `confirmation_id`.
2. Claude Code always declares elicitation. It shows the question only in its interactive terminal. When it runs inside a host app (Claude Desktop, SDK hosts) that gives it no question handler, it answers `{"action":"decline"}` at once. Seen in the Claude Code 2.1.327 code: `if (this.onElicitation) {…} return {action:"decline"}`.
3. The server treats any non-accept answer as the user's "no" (`rejected_by_user`) and never falls back to the code.
4. Reproduction: the real server (throwaway vault, write actions on, no Siigo credentials) under `claude -p`. The debug log shows `Elicitation request received in print mode: mode=form fields=["approve"]`; the tool returned the message above.

Notifications are not involved.

## 3. Second bug found

Claude Code hides `siigo_create_voucher_misc_income` and `siigo_create_journal`: their input schema lists a required field twice inside `body.items`, which the Claude API rejects ("must NOT have duplicate items"). Fix: remove the duplicate `required` entries in the catalog, and add a test that no schema has duplicate `required` items.

## 4. Proposed fix (recommended options)

- **Approval window from the Siigo app** for every write: the tray app shows "Approve this write in Siigo?" with the action, the main fields, and a "Show details" part. Approve or Reject. The AI can't answer it.
  - The tray app is always running while writes are on (quitting it turns writes off), so the window is always possible.
  - The HTTP server runs inside the tray app: it shows the window directly. A stdio server (started by the AI app) asks the tray app over a local channel protected by the private key. If the tray app doesn't answer (for example after a crash), the write is refused.
  - On timeout (no answer): the write is refused and the AI is told "Nobody answered the approval window."
- The AI app's question (elicitation) and the code are no longer used for approval. The `confirmation_id` stays only as a fallback if the owner chooses it (W1 option C).
- Clearer messages: "Rejected in the Siigo approval window" vs "Nobody answered".
- Tests: an automatic decline from the client never sends anything; the window's Approve sends exactly one request; Reject, timeout, and "tray app not reachable" send nothing.
- Release `v0.1.1` (fix) before the one-click plan (`v0.2.0`).
